## 一、结论先行

**一句话结论：真正未动工的架构级项只有 3 条，不是"贝叶斯更新"也不是"ML 训练管线从零建"——这两件事早已做完大半，缺的是「统一编排」和「生产切换决策」，不是从零开发。**

| 领域 | 现状一句话 | 是否架构级缺口 | 建议动作 |
|------|-----------|:--------------:|----------|
| **贝叶斯增量更新（P1-B）** | 基模 + EKF 增量 + shadow 双跑 + 每日计划任务 **全部已落地**，处于「等样本切生产」阶段 | ❌ 不是（已完成，等决策） | **不写代码**，等新赛季 McNemar 统计显著后切流 |
| **ML 训练管线** | 已有 6+ 散件（auto_train / online_learning / scheduled_learning / retrain_trigger / multitask_trainer / mlflow_repro），**多头并发、无单一事实源** | ✅ 是（整合债） | 路线 A：统一编排器 `pipeline/training_orchestrator.py` |
| **跨语言共享核心库** | Python `prediction_core.py` 与 JS `shared/prediction-engine.js`(1955 行) **双份手写**，靠 JSON 桥 + CI 补丁对齐 | ✅ 是（技术债，Skew 复发根因） | 路线 B：Python 单权威 + JS 代码生成 |
| **NN / 时序模型探索** | 已有 `nn_vs_tree_wdl_experiment.py`（PyTorch vs LGBM 对照），未进 Stacking 候选 | ⚠️ 中等（实验项） | 路线 C1：漏斗化门禁，有增益才进候选 |
| **次级联赛数据源** | 暂无次级联赛数据（升班马冷启动靠层级先验收缩） | ⚠️ 中低（数据基建） | 路线 C2：先做数据源探针再决定 |

**推荐优先级：路线 A > 路线 B > 路线 C**。路线 A 投入最小、消除最实的隐患；路线 B 是真正的架构债但工作量最大，建议等 P0-E 实盘 300 注结论出来后再启动；路线 C 放远期。

### 2.2 ML 训练管线——6+ 散件，缺统一编排

| 散件 | 文件 | 职责 | 与其他散件关系 |
|------|------|------|----------------|
| 全量周训 | `scripts/auto_train.py` + `scripts/setup_scheduler.py` | 每周一 02:00 全量重训 | `FootballModelAutoTrain` 计划任务，独立运行 |
| 在线学习管理器 | `scripts/online_learning_manager.py` | 4 类：PerformanceMonitor / IncrementalLearner / ModelVersionManager / OnlineLearningManager | 性能监测 + 衰退检测 + 增量训练 + 版本管理，自成体系 |
| 定时学习调度器 | `scripts/scheduled_learning.py` | APScheduler，每日检查 + 每 168h 重训，可切 multitask | 依赖 `online_learning_manager.run_online_learning_check()` + `multitask_trainer` |
| 重训触发器 | `scripts/retrain_trigger_runner.py` | 三重触发（定时/新数据/周期）+ 性能门禁（平局召回 + 预测率偏差） | T-005 v3 专用，trigger state 在 `deployment/` |
| 训练主入口 | `scripts/train_models.py` / `scripts/advanced_model_trainer.py` / `scripts/multitask_trainer.py` | 三套训练入口，特征开关/模型集不同 | 无统一入口，各脚本各自特征构建 |
| Pipeline 编排 | `pipeline/pipeline_d_to_e_orchestrator.py` / `pipeline/pipeline_F0F1_orchestrator.py` / `pipeline/f1b_progress_monitor_and_post_pipeline.py` | 数据采集→特征→模型的分段流水线 | 偏数据管线，不涉训练决策 |
| 可复现快照 | `scripts/mlflow_repro.py` | git commit + DB 版本 + 特征集版本 sha1 | 被 `train_models.py` 和 `advanced_model_trainer.py` 双入口复用 |

**核心问题**：
1. **多触发器并发**：`auto_train`（每周一）+ `scheduled_learning`（每 168h）+ `retrain_trigger`（三重触发）三套重训调度互不感知，可能在同一窗口跑两次全量重训。
2. **两套衰退判据平行**：`online_learning_manager.PerformanceMonitor.degradation_score` 与 `retrain_trigger` 的平局召回/预测率偏差，两套阈值、两套口径。
3. **无单一事实源**：训练记录散在 `deployment/trigger_state.json`、`assets/*.pkl` mtime、`model_versions` 表、mlflow run——没有一张「训练运行主表」。

### 2.3 跨语言共享核心库——双份手写，Skew 复发根因

| 层 | Python（唯一权威） | Node/JS（影子实现） | 对齐方式 |
|----|:------------------:|:------------------:|----------|
| 预测内核 | `scripts/prediction_core.py`（CalcEngine：DC λ / WDL / Stacking / 校准） | `shared/prediction-engine.js`（**1955 行手写**） | 无自动对齐，靠人工维护 |
| 常量配置 | `prediction_core.py` 内常量 + `config.yaml` | `prediction-engine.js` 硬编码 `DEFAULT_STACKING_WEIGHTS` / `WEATHER_IMPACT` / `SURFACE_IMPACT` | 无同步机制 |
| 特征构建 | `features/sofascore_pre_match_features.py` + `feature_utils.py`（208 维） | `server/services/feature-bridge.js`（读 JSON 桥） | 桥接方案已建（C-20260910-011），但 29 维条件输出未接入 |
| 特征对齐测试 | — | `tests/verify-feature-alignment.js` | 254 维全量校验，白名单外缺失即 FAIL |

**当前 Train-Serving Skew 的解法 = "补丁叠加补丁"**：
- P0-D 根治了一次（C-20260910-004，254 维完全一致）
- 然后用 feature-bridge 补了 110 维（C-20260910-011）
- 但**预测内核本身（DC λ 计算、Stacking 融合权重、校准温度）**仍是双份手写，每次改 `prediction_core.py` 都存在"忘了同步 JS 端"的风险。

### 2.4 NN / 时序模型——实验脚本已存在，缺漏斗化门禁

- `scripts/nn_vs_tree_wdl_experiment.py`：PyTorch（Embedding + MLP backbone + Neural Poisson 比分头 + Focal Loss）vs LightGBM，同 time-series split 对照
- `scripts/t006_score_predictor_v5.py`：比分预测 v5 原型

## 三、路线 A：ML 训练管线统一编排（高性价比，推荐先做）

### 3.1 目标
消除"多触发器并发 / 两套衰退判据 / 无单一事实源"三个问题，所有训练决策汇聚到一个唯一编排器。

### 3.2 改造路径

| 阶段 | 交付物 | 内容 |
|------|--------|------|
| 阶段 1：建表 | `data/odds.db::training_runs` 表 | 字段：run_id(自增) / trigger_source / training_type(full/incremental/bayesian_shadow) / feature_version / model_version / data_window_start/end / val_rps / val_logloss / val_acc / val_draw_recall / started_at / finished_at / status(running/success/failed/skipped) / error_msg / artifacts_json |
| 阶段 2：统一决策 | `pipeline/training_orchestrator.py::should_retrain()` | 合并三套判据为一张决策表：①周期触发（距上次全量 ≥ 7 天 → full）②衰退触发（ECE Δ > 5pp 或 Acc 降 > 3pp → full）③新数据触发（新增已赛场次 ≥ 30 场 → incremental）④去抖：同类型 24h 内不重复 |
| 阶段 3：统一入口 | `pipeline/training_orchestrator.py::run_training()` | 统一调用三个训练入口：全量→train_models.py（208 维生产特征）、贝叶斯增量→bayesian_incremental.py（EKF roll）、多任务→multitask_trainer.py（保留备选）。产物统一写 assets/，刷新 feature_bridge.json，写 training_runs 表 |
| 阶段 4：收口触发器 | 修改 3 个散件 | auto_train.py 改为仅调 orchestrator.run_training(trigger=scheduled)；scheduled_learning.py 改为仅调 orchestrator.run_daily_check()；retrain_trigger_runner.py 改为仅调 orchestrator.should_retrain(new_data) 判定。保留计划任务入口不变，但内核只有一个 |
| 阶段 5：可视化 | `reports/training_runs_dashboard.md`（自动生成） | 最近 20 次训练运行的指标趋势图，触发原因分布，成功率 |

### 3.3 验收标准
- ✅ 任意 24h 窗口内，同类型训练最多跑 1 次
- ✅ 所有训练运行可通过 training_runs 表追溯（trigger → 特征版本 → 模型版本 → 指标）
- ✅ 不影响现有生产链路（预测、报告、EV 决策全不变）
- ✅ py_compile + pytest 通过（新增强制去抖单元测试）

### 3.4 风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|:----:|:----:|------|
| 编排器自身 bug 导致漏训 | 低 | 中 | 保留 --force 手动触发 + 每日 healthcheck 检查 |
| 训练时间窗冲突（数据仍在写入） | 中 | 低 | 加「数据写入静止 30 分钟」门禁 |
| 三套判据参数调优工作量 | 中 | 低 | 首版用保守阈值（等同现有各散件阈值），后续调优 |

### 3.5 工作量估算
- 核心代码：~800 行（编排器 + 决策表 + 状态机）
- 测试：~200 行（去抖 / 决策表分支 / 状态回滚）
- 文档：1 份
- **总工作量：3~5 天**

## 四、路线 B：跨语言共享核心库重构（真正架构债，工作量最大）

### 4.1 目标
Python CalcEngine = 唯一权威 → 自动生成 JS 端纯函数代码 → Node 服务端不再手写预测内核，从根上杜绝 Train-Serving Skew 复发。

### 4.2 改造路径

| 阶段 | 交付物 | 内容 |
|------|--------|------|
| 阶段 1：差异盘点 | `docs/calc_engine_diff_inventory.md` | 逐项列出 prediction_core.py::CalcEngine 与 shared/prediction-engine.js 的函数级差异清单（含硬编码常量、Stacking 权重、校准参数、DC 修正公式） |
| 阶段 2：代码生成器 | `tools/generate_js_calc_engine.py` | Python 侧用 AST 遍历 + 装饰器标记，把标注了 @export_to_js 的纯函数（含常量）转译为等价 JS 代码。输出 shared/calc-engine.generated.js（纯函数、零 IO、与 Python 同输入同输出） |
| 阶段 3：CI 一致性测试 | `tests/test_calc_engine_cross_lang.py` + `tests/verify-calc-engine.js` | 同一组 100 条随机输入（λ_home/λ_away/赔率/特征）→ Python 和 JS 分别跑 → 输出误差 < 1e-9 即 PASS |
| 阶段 4：替换影子实现 | 修改 `shared/prediction-engine.js` | 把 DC 计算 / WDL 概率 / Stacking 融合 / 校准 四类纯函数全部替换为调用 calc-engine.generated.js，保留的仅为 IO/编排/缓存层 |
| 阶段 5：删除冗余 | — | 删除手写的影子实现代码（保留生成器 + 一致性测试作为永久门禁） |

### 4.3 验收标准
- ✅ 同一组 100 条随机输入，Python ↔ JS 输出差 < 1e-9
- ✅ 改 prediction_core.py 中 @export_to_js 函数后，CI 自动重新生成 JS 并跑一致性测试
- ✅ shared/prediction-engine.js 代码量从 1955 行降到 ≤ 500 行（只留 IO/编排）
- ✅ Node 服务端预测结果与 Python 离线预测结果完全一致

### 4.4 风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|:----:|:----:|------|
| Python 语法（装饰器、默认参数、numpy 调用）JS 转译覆盖不全 | 高 | 中 | 第一版只转「标量浮点 + 基础数学函数」子集，超出范围的用 fallback 报错，不强行全量 |
| 浮点精度差异（Python numpy float64 vs JS Number） | 中 | 低 | 验收阈值 1e-9 已考虑；DC 修正/Poisson PMF 逐格对比验证 |
| 改造期服务端不稳定 | 中 | 高 | 灰度：生成的 JS 先作为「shadow 模式」双跑 1 周，全量一致才切流 |

### 4.5 工作量估算
- 差异盘点：1 天
- 代码生成器：5~7 天（AST 遍历 + 转译器 + numpy 函数映射表）
- CI 一致性测试 + 灰度：3 天
- 替换 + 清理：2 天
- **总工作量：11~13 天**

### 4.6 前置条件
- 路线 A 已完成（单一事实源 + 稳定训练节奏，避免双线作战）
- P0-E 实盘 300 注有结论（避免大改造期间影响实盘数据）

## 五、路线 C：NN/时序漏斗化 + 次级联赛（远期）

### 5.1 C1：NN 模型漏斗化门禁

**目标**：把 `nn_vs_tree_wdl_experiment.py` 从「单次实验脚本」升级为「可重复、可回归、有门禁的候选模型漏斗」。

**步骤**：
1. 固化评估口径：与 P1-10/P1-11 同一套流程（LoO → 分组 ablation → 2-fold A/B → 四指标门禁）
2. 门禁规则：RPS 不劣化 + Acc 不下降 + DrawRecall 不低于基线 -2pp → 进入 Stacking 候选池
3. 不达标则**归档结论**（和 P1-10 情境特征一样，正式宣布「NN 无增益」，关闭议题）
4. 达标则走 stacking_ensemble.py 候选模型集 → 进入 shadow 双跑 → 评估生产切换

**工作量**：2~3 天

### 5.2 C2：次级联赛数据源探针

**目标**：先摸清德乙 / 英冠 / 西乙在 SofaScore / Understat / 500.com 的覆盖度，再决定是否投入。

**步骤**：
1. 写 `scripts/secondary_league_probe.py`：分别查三个数据源 23/24、24/25、25/26 三赛季的场次、赔率、xG 覆盖率
2. 输出覆盖度报告
3. 决策：若 ≥ 2 个联赛 × ≥ 2 赛季数据可用 → 立次级联赛采集项；否则维持贝叶斯层级先验方案

**工作量**：1~2 天
