## 一、设计目标与约束

### 1.1 目标

- 构建**五大联赛（英超/西甲/意甲/德甲/法甲）赛果预测全栈系统**，核心交付物为高质量**概率预报**（WDL 胜平负 / 让球 / 比分 / 总进球四任务）。
- 主模型目标 = **高质量概率预报**（RPS、可靠性校准 ECE），**不以投注 ROI 作为训练与验收目标**（实验红线 §15.3）。
- 打通「采集 → 特征 → 训练 → 推理 → 预测/报告 → 赛后复盘 → 知识库 → 重训」**闭环**。

### 1.2 约束

| 约束 | 内容 |
|------|------|
| 双运行时 | **Python 训练离线侧 + Node.js 推理在线侧**，训练产物双写 pkl（Python）+ `*_export.js`（Node） |
| 单一配置源 | `config.yaml` 全局配置单一来源（D3），Node 运行时读 yaml，禁止 JS 硬编码阈值 |
| 数据隔离 | `odds.db`（训练库，1.6GB+）与 `five_leagues.db`（生产业务库）分离 |
| 时序防泄漏 | 训练/回测/校准一律 `TimeSeriesSplit` + 无 shuffle |
| 幂等写库 | `INSERT OR IGNORE` + `UNIQUE` 约束；连接 `busy_timeout=5000` |
| 队名归一 | 入库/查询统一 `normalize_team_name()` / `TEAM_NAME_MAP` |
| 路径动态 | 所有脚本用 `Path(__file__).resolve().parent` 定位，禁止硬编码盘符 |

### 3.2 赔率时序存储（4 表 + 桥接）

| 表 | 覆盖场次 | 对齐率 | 玩法字段 |
|----|---------|-------|---------|
| `wdl_history` | ~12,575 | 98.3% | `win_a`(主胜) / `draw` / `win_b`(客胜) |
| `handicap_history` | ~13,125 | 98.3% | `hcp_win` / `hcp_draw` / `hcp_lose`（让球） |
| `total_goals_history` | ~13,126 | 98.3% | `goals_0` ~ `goals_7_plus` |
| `score_history` | ~13,122 / 81.6 万行 | 63.8% | `score` + `odds`（正确比分） |

- 双通道对齐：`match_id_en` 直连（77.3%）+ `match_id_mapping` 桥表（95.0%）→ 合并 98.3%。
- 6 种桥接策略（按优先级）：`cn_to_en → substring → direct → sofascore → fuzzy_date → date_tolerance(±1天)`。

### 3.3 Understat xG 三表（`understat_schema.md`）

- `understat_match_team_stats`（比赛级，主键 `match_id`）：比分/xG/赛前 `forecast_w/d/l`。
- `understat_player_xg`（球员级，复合主键 `(match_id, player_id)`）：xG/xA/`xg_chain`/`xg_buildup`（Understat 独有）。
- `understat_shots`（射门级，主键 `shot_id`）：坐标/部位/情况/结果，用于射门地图与进球质量。

### 3.4 数据库访问适配层（`db_utils.py`，P2-11）

- 职责：SQLite / PostgreSQL **双后端统一访问**，屏蔽两后端方言差异（`?` → `%s` 占位符转换、`sqlite3.Row` 风格键访问）。
- 核心 API：`connect(backend=...)`（默认 SQLite `data/odds.db`，PG 走环境变量 `PG_HOST/PORT/USER/PASSWORD/DB`）、`read_sql`（替代 `pd.read_sql`）、`write_dataframe`（替代 `df.to_sql`）、`table_exists`、`numeric_sql_type`。
- 后端选择：`connect(backend=...)` > 环境变量 `DB_BACKEND`（默认 `sqlite`）。
- 调用范围：被 `features/`、`scripts/`、`modules/common/` 下 **21 个模块** import。其中 **17 处在生产离线链路**（`feature_utils.py` 主引擎 + score/tg/hcp/odds_consensus/xg_deep 特征模块 + `data_loader`/`backtest_engine` + 3 个 `features/` 赛前特征模块 + `player_data_analysis`），4 处在离线回测/评估（`backtest_full_three_way*` + `compute_hitrate_3matches`），其余 4 处为 `_` 前缀临时诊断脚本（非生产）。
- **接入边界**：仅服务于**离线训练/特征工程/回测链路**（§10.1 训练数据流），**不参与线上推理服务**——线上走 Node.js Express + better-sqlite3（§10.2），通过 `assets/*_export.js` 模型导出物间接衔接，与 Python `db_utils.py` 无直接交互。

## 五、模型/训练层

### 5.1 WDL 主模型（生产链路 `train_models.py`）

- **Stacking = 5 基础模型 + LR meta-learner**：Dixon-Coles（泊松/DC）+ Elo + XGBoost + LightGBM + 贝叶斯层级（Baio-Blangiardo HBM）。
- 训练流程：`load → 质量门禁 → build_all_features(254维) → 样本权重(异常3.0/双误4.0 + L3知识库 + 人工修正1.2) → TimeSeriesSplit(5) → XGB/LGB → Platt校准 → 平局后处理校准(召回≥0.28约束) → 分层评估 → MLflow → 双写 pkl + *_export.js`。
- 当前超参（config.yaml `model.*`，Optuna 搜索）：XGBoost `max_depth=4, min_child_weight=13, gamma=4.956`（反过拟合）；LightGBM `max_depth=3, num_leaves=202, min_data_in_leaf=23`。
- **OOF RPS = 0.1984**（Stacking 优于固定权重 0.2038）。

### 5.2 各子模型

| 子模型 | 文件/产物 | 维度 | 状态 |
|--------|----------|------|------|
| T-005 让球/方向 | `t005v3_direction_predictor.pkl` + `draw_detector.pkl` | 71 维（LightGBM） | v3 生产，准确率 53.80% |
| T-006 比分 | `score_prediction_module.py`（DC + IPF + Monte Carlo） | DC 体系 | **v5 生产** |
| 总进球 | `TotalGoalsPredictor` | — | 生产 |
| 统一引擎 | `unified_prediction_engine.py`（DixonColesGenerator） | 四维统一导出 | enabled=false（当前走 T-005/T-006 独立） |

### 5.3 T-006 v5 比分核心（`t006_score_predictor_v5.py`）

1. **λ 数值求解**：二分法（45 迭代）求解强度差 d 使泊松胜负倾向精确对齐去水 WDL 概率（替代 v4 的 `λ=2.8×胜率` 启发式）。
2. **IPF 乘性重加权**：30 轮迭代按 WDL 三边缘缩放比分网格，构造性精确对准目标概率。
3. **DC τ 修正**：`1.0 - lh*la*rho`；联赛 ρ：英超-0.08 / 西甲-0.12 / 意甲-0.15 / 德甲-0.05 / 法甲-0.10。

### 5.4 训练调度（现有多散件）

`auto_train.py`（每周一 02:00 全量）+ `online_learning_manager.py`（衰退检测）+ `scheduled_learning.py`（APScheduler）+ `retrain_trigger_runner.py`（三重触发）+ 三套训练入口（`train_models.py` / `advanced_model_trainer.py` / `multitask_trainer.py`）。

> ⚠️ 缺陷：多头并发、无单一事实源 → 见 §14 路线 A。

## 八、赛后复盘与知识库闭环

### 8.1 A 模块：赛后复盘闭环（已全落地）

```
SofaScore collect_post_match (A2) → run_post_match_pipeline.py
  → post_match_schema.py 写 post_match_review (A1, UNIQUE match_id)
  → model_predictions 追加 actual_wdl/score/tg/hcp 4 行 (幂等)
  → attribution_engine.py 8 维度归因 (A3, 纯规则无 LLM)
  → generate_post_match_report.py 复盘报告 (A4, 8 章)
  → confidence_review.py 可信度分级 (A5)
  → quality_gate --review 数据质量门禁 (A6, data_quality_score<0.7 排除)
```

- **归因引擎（A3）** 8 维度：数据缺失 / 赔率异动 / 阵容异动 / 运气偏差(xG) / 异常事件 / 战意 / 模型局限性 / 校准偏移。
- **⚠️ 平局归因方向已反转**：模型平局概率**系统性高于市场**（非召回不足），维度 8 触发「平局过度自信」，禁止写「平局样本×1.2 加权」。

### 8.2 B 模块：知识库与闭环进化（已全落地）

- 目录：`data/knowledge_base/{英超/西甲/意甲/德甲/法甲/global}/{feature_insights.json(L2) / sample_weights.json(L3) / rules.json(L1)} + human_corrections.json`。
- 可信度分级：1 纯模型 / 2 部分外部 / 3 完整外部 / 4 人工确认 / 5 同类≥3 场重复验证；**≥4 级才写因子库**。
- 消费：L1 规则直接应用；L2 只展示不自动改参；L3 重训时作样本权重建议；人工修正 `human_corrections.json` 三级消费（规则覆盖/样本权重/上下文记忆）。
- 优化建议**不自动执行**，须人工确认后触发重训（A/B 四指标门禁）。

## 十四、架构级深水项改造路线

> 依据《架构级深水项改造方案.md》：真正未动工的架构级项只有 3 条，缺的是「统一编排」与「生产切换决策」，不是从零开发。

### 14.1 路线 A：ML 训练管线统一编排（高性价比，推荐先做）

- 问题：`auto_train`(每周一) + `scheduled_learning`(168h) + `retrain_trigger`(三重触发) 三套调度互不感知；两套衰退判据平行；训练记录散落无主表。
- 方案：`pipeline/training_orchestrator.py` + `training_runs` 表（run_id/trigger_source/training_type/指标/status），统一 `should_retrain()` 决策表 + `run_training()` 入口 + 收口三散件。
- 工作量：3~5 天。验收：任意 24h 同类型最多 1 次；training_runs 全追溯。

### 14.2 路线 B：跨语言共享核心库重构（真正架构债，工作量最大）

- 目标：Python `CalcEngine` = 唯一权威 → AST 转译自动生成 JS 纯函数 → 从根杜绝 Skew 复发。
- 路径：差异盘点 → `tools/generate_js_calc_engine.py` → CI 一致性测试（<1e-9）→ 替换 `prediction-engine.js`（1955→≤500 行）→ 删除冗余。
- 工作量：11~13 天。前置：路线 A 完成 + P0-E 出结论。

### 14.3 路线 C（远期）

- C1：NN 模型漏斗化门禁（LoO → ablation → 2-fold A/B → 四指标门禁 → 达标进候选池）。
- C2：次级联赛数据源探针（德乙/英冠/西乙覆盖度摸底再决策）。

### 14.4 优先级矩阵

| 路线 | 投入 | 收益 | 前置 | 优先级 |
|------|:----:|------|------|:------:|
| A 训练管线统一编排 | 小(3-5天) | 中高 | 无 | 🔴 最高 |
| B 跨语言共享核心库 | 大(11-13天) | 高 | A + P0-E | 🟡 中期 |

## 十五、工程规范与避坑

### 15.1 硬性约束

- `matches.handicap` 只允许竞彩（`handicap_source='sporttery'`）写入，非竞彩源由数据库触发器阻断（`trg_guard_matches_handicap_ins/upd`）。
- 亚盘半盘口（如 1.75）隔离在 `odds500_match.handicap`，不混入 `matches.handicap`。
- `team_name_mapping.py` 的 `TEAM_ALIASES` 禁止含通用英文词（City/United/Madrid），防子串误归一（Coventry City→曼城教训）。
- 路劲动态定位，禁硬编码盘符。

### 15.2 避坑经验

- match_id 生成前必须队名归一，否则预测与 SofaScore 数据 join 失败。
- 500.com 半整数亚盘 与 竞彩整数 goalLine 混用导致让球结果错误（上盘赢 vs 走水），已隔离。
- 文档自动更新机制：每次改动同步 `docs/change_log.md`（C-YYYYMMDD-NNN）+ `§5 统计表`，涉及数据采集同步 `data_collection_progress.md`，涉及规则同步 `project_memory.md`。

### 15.3 实验红线（必须遵守）

1. ❌ 不再尝试 EV-policy 直接求导自定义 Loss / MOD 市场蒸馏 KL 损失。
2. ❌ 不再尝试 Focal Loss / 大幅放大平局样本权重（9 组网格证伪）。
3. ❌ 不再大规模做离线 EV 阈值/凯利/置信网格搜索——投注假设必须 C1 实盘验证。
4. ❌ 不重新启用 P1-10 情境特征 / P1-8 xG 深化 / P2-10 位置球员特征（除非 Opta 原始事件流）。
5. ❌ 不把投注 ROI 作为主模型训练与验收目标。
